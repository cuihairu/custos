# LuCI 配置写入契约（C-SET-UX-04/05 实施前定义）

状态：契约定义（2026-11-24，随 C-SET-UX-01/02/03 实现批产出）。本文档是 04（预览/备份/提交）与 05（保存后确认进程状态）的实施契约，实施与验收在后续批次。

## 1. 现状与缺陷（实施 04 要消除的）

当前写入路径 `packaging/openwrt/usr/lib/lua/luci/controller/custos.lua` 的 `apply_write`：

1. `cp -p <path> <path>.bak` —— 先覆盖备份；
2. 写 `<path>.new`；
3. `custos validate <path>.new`；
4. 校验通过才 `mv -f` 替换并重启。

缺陷：**校验失败时备份已经被第 1 步覆盖**。上一轮保存留下的「上一份可用配置」备份会被一次注定失败的提交破坏——虽然 live 文件未动，但回滚材料丢了。此外 `cp`/`mv` 的退出码未逐一核实，重启命令的返回值被丢弃（05 的问题）。

## 2. 写入契约（04 实施顺序，不可调换）

```
① 预览   字段级 diff（当前值 vs 新值），仅列改动项；令牌类字段显示「已更改（隐藏）/未更改」，永不回显明文
② 构建   tomledit 渲染候选全文 → 写同目录临时文件 <path>.new（同文件系统，mv 原子）
③ 校验   /usr/bin/custos validate <path>.new；RC≠0 → 删除临时文件、原样返回校验输出（含行号），
         live 文件与 .bak 均未被触碰 —— 到此为止失败零副作用
④ 备份   仅校验通过后：cp -p <path> <path>.bak；核实复制退出码为 0 且 .bak 可读、非空
         （大小或 md5 与 live 一致）；备份失败 → 中止，live 未动
⑤ 替换   mv -f <path>.new <path>；失败 → 保留 live 与 .bak，报错
⑥ 重启   /etc/init.d/custos restart → 按 §3 的状态反馈模型回报
```

- **失败不变量**：任何一步失败，live 配置保持上一可用版本；`.bak` 只在 live 即将被成功替换的前一刻更新。
- **并发**：请求携带编辑基线（客户端读取时的文件 md5）；写入前比对当前文件 md5，不一致 → 拒绝（JSON 错误「配置已被其他会话修改，请刷新后重试」），不覆盖他人改动。
- **认证**：沿用现有 `luci.dispatcher.test_post_security()`（POST + token），不新增旁路。
- **错误定位**：结构化表单错误定位到字段（现有 `validate_resource` 逐项返回）；TOML 级错误透传 `custos validate` 输出的行号/列号，行号与渲染后文档 1:1 对应。
- **无改动提交**：预览 diff 为空 → 应用按钮禁用；服务端渲染结果与 live 逐字节相同 → 跳过备份与重启，返回「无改动」。

## 3. 状态反馈模型（05）

重启结果与写入结果分离，四态：

| 状态 | 含义 | 判定 |
|---|---|---|
| `written` | 配置已落盘，等待服务确认 | ⑤ 成功、⑥ 已发出 |
| `confirmed` | 服务已用新配置运行 | 重启后轮询 `/etc/init.d/custos status`（间隔 ~500ms，上限 ~5s）出现 exit 0 |
| `restart_failed` | 重启命令非零退出或超时窗口内未 running | 保留错误输出 + `.bak` 路径入口；提供「用备份恢复」动作（恢复本身也走 ②–⑥，恢复后同样确认状态） |
| `stopped_by_user` | 用户主动停用（UCI enabled=0） | 不当作失败；显示已停用与当前生效配置来源 |

轮询期间 UI 显示「待服务确认」，不阻塞其他页面操作。

## 4. 验收清单（实施 04/05 时逐句核对）

- 正常保存 / 无改动 / 依赖环 / 损坏 TOML / 备份失败 / 并发写 / 写入失败：核对配置与备份哈希、失败时上一份可用配置在位。
- 重启：正常 / 非零退出 / 启动后退出 / 用户停用：进程状态与 UI 四态一致。
- 令牌：预览、诊断、日志三处均不出现明文。
