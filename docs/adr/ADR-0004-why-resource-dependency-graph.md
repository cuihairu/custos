# ADR-0004: 为什么采用 Resource + Dependency Graph

- 状态：已接受
- 日期：2026-10-31
- 关联：docs/guide/resources.md §3，ADR-0005

## 背景

真实故障的正确处理由拓扑决定：数据库挂了，应用的重启毫无意义；代理断了，
Tunnel 的"恢复"只会空转。资源不是平铺的监控项，而是一张有向依赖图。

## 决策

`Resource` 描述对象（探针、健康策略、恢复策略），`Dependency` 描述前置条件
（required/optional/conditional + `HealthCondition`），配置加载期把二者构建为
`DependencyGraph`：悬空引用、重复 ID、不可能条件、环都在启动期报出具体字段路径，
拒绝启动而不是运行期死锁。

## 替代方案

- **平铺资源列表**：恢复无顺序语义，"先修 db 再修 app"无法表达。
- **隐式探测顺序（按配置顺序）**：顺序是巧合不是语义，改配置顺序即改行为。
- **运行期动态发现依赖**：无验证时机，错误发现得越晚代价越大。

## 优缺点

优点：恢复顺序可推导（拓扑序）；启动期把所有结构性错误一次性拒绝；
条件依赖（`conditional_on`）与备选组（`alternative_groups`）表达冗余与降级语义。
缺点：建模学习成本；配置错误在启动期暴露（这是特性不是缺陷）。

## 后续影响

- graph.rs 的环检测返回具体环路径（ADR-0014）。
- 引擎的 waiter 去重（§3.6）建立在图语义上：同一依赖的所有等待者共享一次恢复结果。
