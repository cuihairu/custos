# 17. ADR：必须记录的架构决策

以下决策需要以 ADR 形式落档：

1. 为什么选择 Rust。
2. 为什么第一版采用外部进程插件。
3. 为什么选择 JSON-RPC over stdio。
4. 为什么采用 Resource + Dependency Graph。
5. 为什么依赖图由 Core Engine 协调。
6. 为什么动作结果必须经过独立验证。
7. 为什么使用 SQLite。
8. 为什么恢复动作前必须持久化关键状态。
9. 为什么通知系统与恢复引擎解耦。
10. 为什么 Dashboard 默认关闭。
11. 为什么 P0 只实现 Process 和 Exec Probe。
12. 为什么不允许未经授权的高风险网络动作。
13. 为什么未知执行结果不能直接重试。
14. 为什么禁止普通依赖图循环。

ADR 必须记录背景、决策、替代方案、优缺点和后续影响。

# 18. 最终实施原则

Custos 的成功标准不是能够监控多少种服务，而是遇到真实故障时，能够正确判断依赖、执行适当的恢复动作、验证结果，并留下完整记录。

整个系统应遵循：

**资源负责描述对象，依赖负责描述前置条件，插件负责提供能力，策略负责决定动作，核心引擎负责协调执行，验证负责判定结果，持久化负责保留事实，通知负责传递事件，Dashboard 负责可选展示。**

第一阶段必须先把核心恢复闭环、依赖语义、持久化和失败处理实现正确。后续再逐步加入 Windows 网络恢复、代理、Cloudflare Tunnel、OpenClash 和其他平台能力。

不要一次性实现所有插件，也不要提前构建复杂的 Dashboard 或插件市场。

先用最小但完整的恢复闭环证明架构，再根据真实部署中无法处理的故障逐步扩展。



## 给 Code Agent 的第一条执行指令

文档已经明确整体目标，但真正开始实施时，我建议先把下面这段单独交给主 Agent，让它先检查仓库并执行 P0，而不是立即实现所有阶段。



rules:
    - event: recovery.exhausted
      severity: critical
      channels:
        - primary-webhook
```

需要注意：

1. 代理健康检查应尽量区分代理认证失败、连接失败和目标服务异常。
2. 如果代理并非 Tunnel 的必要依赖，则不应声明 Required。
3. HTTP 探测和上述特定插件属于后续阶段能力。
4. 第一版的配置验证器可以先定义完整配置模型，但未实现的资源类型必须报出清楚的能力缺失错误，不能假装已经运行。
5. 恢复动作必须与插件能力声明匹配。

## 10.3 配置加载过程

1. 解析配置。
2. 验证版本。
3. 验证结构。
4. 验证资源 ID。
5. 验证依赖引用。
6. 验证依赖图。
7. 验证恢复动作引用。
8. 验证插件能力。
9. 验证权限与风险策略。
10. 验证通知渠道配置。
11. 验证数据库迁移兼容性。
12. 创建或更新运行时资源注册表。

配置验证失败时必须指出具体字段和原因。
