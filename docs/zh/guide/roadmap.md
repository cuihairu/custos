# 14. 分阶段实施计划

## P0：核心恢复引擎

目标：先实现完整且可测试的恢复闭环，不接入复杂网络能力。

实现内容：

1. Cargo Workspace。
2. Resource、Dependency、Evidence、Diagnosis、RecoveryPolicy、RecoveryRun 等领域模型。
3. 配置解析和验证。
4. 依赖图构建和循环检测。
5. Process Probe。
6. Exec Probe。
7. 连续失败阈值和健康状态转换。
8. RecoveryRun 状态机。
9. 有序候选动作。
10. 恢复动作执行后重新验证。
11. 失败后的重新诊断。
12. 超时、预算和冷却时间。
13. 资源级恢复互斥。
14. SQLite 持久化。
15. 崩溃恢复和未知结果处理。
16. CLI 基础命令。
17. 结构化日志与审计事件。
18. 集成测试与故障注入。

P0 不包含：

- HTTP Probe。
- Web Dashboard。
- 远程管理 API。
- 插件市场。
- OpenClash。
- 复杂 Wi-Fi 恢复。
- 企业通知平台。

验收标准：

- 一个进程退出后能被检测。
- 一个受控命令失败后能触发恢复。
- 第一个恢复方案失败时能选择第二个方案。
- 命令返回成功但资源仍异常时，不得报告恢复成功。
- 依赖不健康时，上层动作不会提前执行。
- 同一资源不会并发执行多个恢复任务。
- Custos 崩溃重启后可以恢复未完成任务。
- 结果未知的动作不会被无条件重复执行。
- 所有状态转换都可以通过日志和数据库追溯。
- 所有预算耗尽的任务都能明确终止。

## P1：插件运行时与通知基础设施

实现内容：

1. JSON-RPC 2.0 stdio 插件协议。
2. 插件能力声明。
3. 插件启动、关闭和重启管理。
4. 超时、取消和输出限制。
5. 插件崩溃隔离。
6. NotificationEvent。
7. 本地日志渠道。
8. Webhook 内置渠道。
9. SMTP 内置渠道。
10. 持久化通知队列。
11. 通知重试、去重和死信状态。
12. CLI 通知状态和重试命令。
13. 插件权限与能力检查。

验收标准：

- 插件崩溃不会导致核心进程退出。
- 大量 stderr 输出不会阻塞协议通信。
- 插件无响应会在规定时间内超时。
- 断网期间通知保留在本地队列。
- 网络恢复后通知可以继续发送。
- 通知发送失败不影响恢复任务。
- 敏感字段不会进入普通日志。

## P2：平台基础能力

优先支持 Linux 和 Windows。

实现内容：

- 进程管理。
- systemd 服务控制。
- Windows Service 控制。
- 平台能力探测。
- 平台权限检查。
- 系统重启动作。
- 本机网络基础探测。
- 平台适配器集成测试。

验收标准：

- Linux 不使用 systemd 时能正确报告能力不支持，而不是误执行。
- Windows 服务操作具备超时和结果验证。
- 高风险操作没有明确授权时会被拒绝。
- 平台特有错误能转换为统一的故障结果。

## P3：网络、代理与真实自愈场景

实现内容：

- 网络接口探测。
- 网关和路由探测。
- DNS 探测。
- HTTP Probe。
- 代理连接与认证诊断。
- Mihomo 插件。
- cloudflared 插件。
- Windows Wi-Fi 恢复。
- OpenWrt 网络适配器。
- OpenClash 插件。
- 网络恢复后的端到端验证。
- 网络操作的互斥与风险控制。

验收场景：

1. 向日葵离线，但网络正常：只恢复向日葵相关服务。
2. Wi-Fi 断开：先恢复网络，再验证远程管理能力。
3. 代理正常、Tunnel 异常：重启 Tunnel。
4. 代理异常、Tunnel 异常：先恢复代理，再处理 Tunnel。
5. 代理返回 407：识别认证问题，不直接认定服务宕机。
6. 代理恢复后 Tunnel 仍异常：重新诊断 Tunnel。
7. 所有恢复方案失败：停止自动处理并通知。
8. 恢复期间网络再次断开：本地引擎继续运行并持久化结果。

## P4：可选管理界面与扩展

实现内容：

- Web Dashboard，默认关闭。
- 资源列表与健康状态。
- 依赖图展示。
- RecoveryRun 时间线。
- 通知状态。
- 配置检查。
- 更丰富的通知插件。
- macOS 适配。
- BSD 适配。
- OpenWrt 完整能力。
- 插件签名与分发策略。
- 更完善的操作授权界面。

验收标准：

- Dashboard 默认关闭时无监听端口。
- Dashboard 不可用时核心功能不受影响。
- Dashboard 不直接执行绕过 Core Engine 的动作。
- 高风险操作仍经过统一权限和审计流程。
